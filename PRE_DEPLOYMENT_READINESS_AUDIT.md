# Court4 pre-deployment readiness audit

Audit date: 2026-08-05
Scope: restricted staging only; no deployment, DNS, TLS, cloud resource, or object-storage work was performed.

## 1. Executive summary

Court4 is **not ready for deployment**. The application security model, PostgreSQL migrations/restore, automated backend/frontend suites, production frontend build, and dependency production audit now pass. Promotion remains blocked because real Brevo inbox receipt/link consumption was not demonstrated, the critical upload-to-CV workflow was not run end-to-end with real processing, the current backend source was not rebuilt into an image, the repository contains extensive unreviewed/untracked production source, and the proposed local-storage host capacity/reconciliation is not ready.

## 2. Git state

- Branch `main` is three local commits ahead of `origin/main`; initial head was `bd14ea1`.
- The worktree was already extensively dirty. There were no staged files, but numerous modified and untracked application, migration, email, verification, frontend, tests, docs, and image assets. Those changes include intended Phase 1.8B/1.8C/1.8C.1/Brevo/verification work but are not a trustworthy reviewed release checkpoint.
- `.env`, inputs, outputs, models, build output, caches, logs, test results, and dependencies are ignored. `web/.env*.local` was added to `.gitignore` during this pass.
- `web/AGENTS.md` and `web/CLAUDE.md` were generated by Next.js and remain untracked; landing screenshots/assets/scripts also require owner review.
- No files were staged or committed and no destructive Git command was used. The logical backup remains under ignored `build/`.

Result: **BLOCKED** until intended source/migration/assets are reviewed and committed from a clean checkpoint.

## 3–17. Detailed evidence

### Infrastructure, origins, cookies, and configuration

- Deployment settings fail closed for default signing secret, insecure deployment cookie, development email sink/provider, missing provider key/sender, non-HTTPS frontend link base, implicit registration, registration without an allowlist, malformed/wildcard/credentialed/path origins, and staging/production CORS that differs from the frontend origin.
- Frontend production configuration requires an absolute HTTPS API origin. Verification/reset links use the configured frontend base, not the Host header. Redirect targets are locally constrained.
- CORS credentials are limited to the exact configured frontend origin. Cookie-mutating auth requests validate Origin against the same trusted set.
- Refresh cookies are HttpOnly, Secure in staging/production, explicitly `SameSite=lax`, host-only, path `/api/v1/auth`, and have explicit max-age/expiry. Local HTTP development remains supported intentionally.
- The actual staging URLs, TLS, secrets, deployment PostgreSQL URL, mounted volume, and provenance values do not exist yet; placeholders alone do not satisfy deployment readiness.

### PostgreSQL and backup/restore

- Migration head: `0006_verification_onboarding_handoff`.
- Clean disposable database: upgrade base→head, downgrade to base, re-upgrade to head, and `alembic check` all passed.
- Primary inventory: 11 application/migration tables, database size 9,255 kB. Safe row counts after final restoration: users 7; uploaded_videos 3; analyses 3; analysis_runs 3; analysis_artifacts 663; analysis_state_events 12; idempotency_records 3; player_selections 0; refresh_sessions 7; account_tokens 6.
- Required indexes exist for owner history, active-purpose account tokens, refresh user/family/expiry, idempotency owner/scope/key, and the one-active-run partial constraint.
- `/ready` returns 503 when PostgreSQL is unavailable. PostgreSQL, not filesystem JSON, is runtime authority; ownership foreign keys and owner-scoped queries are enforced.
- A 107,125-byte custom-format backup with SHA-256 `0DFAE7E557A870094F13A4EC2F60D02D15BC67FB77B5CE7ECF7116D960BDE7CB` restored into a separate database. Revision, aggregate counts, and `/ready` passed.
- During validation, a test container inherited the primary database URL and a test fixture truncated local rows. The error was detected immediately from aggregate counts and the backup restored the exact counts above. No user data was intentionally deleted. This is an audit incident and is why the runbook now requires an asserted disposable database name before destructive fixtures.

### Brevo and account controls

- The Brevo adapter and its unit tests pass, configuration is locally SET, and secrets were not printed.
- No approved test inbox/inbox access was available. Real verification, resend, password reset, password-change, and session-security messages were not received or consumed. An HTTP response alone was not treated as delivery evidence.
- Registration requires an explicit deployment choice, an enabled allowlist, normalized approved emails, and typed rejection for non-approved users. Existing login/recovery remains reachable. Central verified-user dependencies and the frontend gate block unverified users from product routes.

### Internal routes, isolation, and logging

- Direct production-like requests and OpenAPI inspection confirmed development email inspection, Active Play debug, and calibration readiness/internal routes are unmounted (404 and absent from schema).
- Bootstrap identity is forbidden in deployment; normal routes require authenticated database users.
- Cross-owner analysis/artifact/history access returns hiding 404 responses; private artifacts are database-owner authorized.
- Structured JSON logging avoids passwords, tokens, cookies, email bodies, API keys, and database URLs in reviewed auth/email paths. Readiness failures now emit a categorized warning. Startup/upload/analysis operational coverage still needs deployment collector/alert proof.

### Docker and disk

- Existing `court4:local` content size: 3,161,053,009 bytes; historical displayed image size was about 9.26 GB. It runs as root, has no container healthcheck, exposes port 8000, and its detector dependency layer includes large PyTorch/CUDA content.
- Compose explicitly runs Alembic before Uvicorn, mounts `./data:/app/data`, and uses a named PostgreSQL volume. The Dockerfile alone does not run migrations. There is no frontend image.
- Docker reported 29.78 GB images, 257.5 MB containers, 931.6 MB volumes, and 32.78 GB build cache (8.922 GB reclaimable). Host C: free space was only 8,061,038,592 bytes.
- The disk runbook requires a 20 GB build reserve. A current backend build was therefore not attempted; the existing image predates this audit's source fixes. Root runtime, missing healthcheck, oversized dependency shape, and unbuilt provenance remain deployment blockers.

### Persistent storage, uploads, and capacity

- `/ready` now checks that the storage root can be created and written via a temporary probe; storage or database failure returns a clear 503 while `/health` remains cheap.
- Relative-path confinement, metadata authority, missing/unknown-file denial, owner-scoped duplicate detection, restart-capable mounted layout, and cleanup on empty/oversize/duplicate staging paths are tested.
- Current `data/output`: 9,833 files, 976,901,098 bytes, versus 663 database artifact records. Reconcile legacy/generated bytes before staging transfer.
- Staging recommendation: 512 MiB maximum video, five test users, three analyses/account operational limit, 35% artifact overhead, at least a 25 GiB data volume, warning below 30%/10 GiB free, hard stop below 15%/5 GiB free, and one processing request at a time.
- Application-level storage quota, proactive disk-full admission control, and processing semaphore do not exist. These require ingress/operational enforcement for the preview.

### Product workflow and health

- Real PostgreSQL-backed browser flows cover landing, registration/verification/onboarding, login/logout/session restore, histories, settings-related auth, desktop/mobile, and cross-layer route behavior.
- The Playwright analysis workflow uses controlled API responses; no real approved video completed court detection→players→selection→analytics during this audit. Duplicate/owner/storage behaviors are covered below browser level but the critical CV chain remains unproven.
- `/health` passed. New-source `/ready` reported database and storage ready; dependency failure tests returned 503. Brevo network is intentionally not called per readiness probe—configuration is startup validated and delivery must be separately monitored.

## 19. Blocking issues

1. Demonstrate actual Brevo inbox receipt and consume verification/reset links plus notification emails from the approved sender.
2. Review and commit the intended source, migration, documentation, and assets from a clean, attributable Git checkpoint.
3. Free sufficient build capacity, rebuild/scan the current backend source, and address or explicitly approve root/no-healthcheck/large-image risks for the selected host.
4. Run the critical workflow with a real approved video and real backend CV processing through final analytics and cross-user checks.
5. Reconcile the existing filesystem with PostgreSQL artifacts and provision/monitor adequate persistent capacity with upload/concurrency hard stops.
6. Provide actual private staging secrets, PostgreSQL, HTTPS endpoints, mounted storage, commit/build provenance, and operational log/alert ownership.

### Non-blocking follow-ups after blockers close

- Upgrade Vitest/Vite through a reviewed major-version change and retire the five development-only advisories.
- Move the runtime to a non-root image, add an image-native healthcheck, and reduce the detector/CUDA dependency footprint in the planned deployment-operations phase.
- Replace operational upload/concurrency limits with narrow application enforcement before expanding beyond five alpha users.
- Add deployed startup/upload/analysis dashboards and alert tests, and obtain legal approval for Privacy/Terms/retention wording.

## 20–21. Exact requirements and recommended order

1. Clean/review Git; choose an immutable commit and build ID.
2. Reconcile data, establish a 25+ GiB persistent volume, and reserve at least 20 GiB for Docker builds plus database/log/backup capacity.
3. Build and scan the backend artifact; publish the frontend build from the same checkpoint.
4. Provision private PostgreSQL and secrets, then configure the exact variables in `STAGING_ENVIRONMENT_CONFIGURATION.md`.
5. Establish TLS/private access, run migration, mount storage, and verify backup/restore before user traffic.
6. Start one backend instance and the frontend; require `/health`, `/ready`, route-security, CORS/cookie, and console smoke evidence.
7. Complete real Brevo flows, then the real video/CV workflow and two-user isolation from `LIVE_STAGING_SMOKE_TEST.md`.
8. Enable the five-user allowlist only after all blocking evidence is signed off.

## 22. Final verdict

**NOT READY FOR DEPLOYMENT**
